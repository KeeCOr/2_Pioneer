1. 문서 메타데이터와 근거 범례

프로젝트명 Pioneer, 문서 버전 1.0, 제품 버전 1.8.2(출처: package.json). 범례: [사실]=package.json/파일 목록에서 직접 확인, [제안]=파일명·설명에서 추론한 미검증 설계안. 본 문서는 persona_playtest_feedback.md 등 서술형 문서의 본문을 열람하지 못해 구조적 근거 위주로 작성됨.

2. 문제 정의

[제안] package.json 설명('ocean trade and fleet-management simulation game')에 근거하면, 플레이어가 한정된 항로·시장 정보 속에서 함대 배치와 무역 타이밍을 잘못 판단해 손실을 보는 문제를 다룰 가능성이 큼. 이는 marketPrices.test.js, routeSummary.test.js 존재로 뒷받침되나 구체 문제 서술은 원문 미확인으로 확정 불가(신뢰도 낮음).

3. 한 줄 피치와 제품 포지셔닝

[제안] "항로를 설계하고 함대를 운영하며 시장 가격 변동에 대응하는 해상 무역 시뮬레이션." 포지셔닝은 캐주얼~미드코어 경영 시뮬레이션 장르로 추정(패키지 설명 기반, 신뢰도 낮음).

4. 주 페르소나

[제안] 김도윤, 34세, 물류회사 대리. 출퇴근 이동 중 짧은 세션으로 항로·재고를 점검하고 점심시간에 시장가를 확인해 매매 타이밍을 잡는 상황을 가정. persona_playtest_feedback.md에 실제 페르소나 정의가 있을 가능성이 높으나 본문 미열람으로 확정 불가(신뢰도 낮음).

5. 디자인 기둥과 핵심 재미

[제안] ①항로 최적화의 퍼즐감, ②시장 가격 타이밍 판단, ③함대 리스크(재고·항해 손실) 관리. navigation.test.js, mapHints.test.js, mapView.test.js 존재가 항로/지도 시스템의 구조적 근거(신뢰도 낮음, 세부 재미 요소는 미검증).

6. 핵심 루프

유저가 선택을 하면 결과가 되고, 그 결과 때문에 다시 선택을 한다.

[제안] 정찰하여 항로를 확인하고, 화물을 적재하고, 항해하여 항구에 도착하고, 시세를 확인해 판매·재보급하고, 다시 정찰하는 과정을 반복한다. fleetTradeFlow.test.js, trade.test.js 존재가 무역-항해 순환 구조의 근거(신뢰도 낮음).

7. 최초 30초 플레이 흐름

[제안] 콘셉트 이미지(Pioneer_gameplay_preview.png)와 유사한 항구/지도 화면 진입 → 보유 함선과 기본 항로 확인 → 첫 화물 적재 및 목적항 선택 → 항해 시작. 실제 온보딩 흐름은 원문 미확인으로 세부 확정 불가.

8. 게임 규칙과 승패 조건

[제안] 명확한 '패배' 조건보다는 자산(자금·함선)의 성장 여부로 성과를 측정하는 경영 시뮬레이션 구조로 추정. 승패보다 KPI형 목표 달성 여부가 중심일 가능성이 있으나 원문 미확인(신뢰도 낮음).

9. 콘텐츠, 진행, 성장, 경제 구조

[사실] marketPrices.test.js, trade.test.js, routeSummary.test.js가 시장가격·거래·항로요약 로직의 존재를 시사. [제안] 함선 확장, 항로 다변화, 시세 변동 대응이 성장 축을 구성할 것으로 추정되나 구체 수치·단계는 미검증.

10. MVP 가설과 검증 방법

가설1: 플레이어는 단순 항로 1~2개만으로도 무역 루프(적재-항해-판매)를 이해하고 반복 플레이한다. 가설2: 시세 변동 정보가 재방문 동기를 만든다. 검증 방법은 소규모 플레이테스트에서 세션당 항해 반복 횟수와 재방문 여부를 관찰하는 것을 제안(현재 관찰 데이터 없음, 신뢰도 낮음).

11. 레퍼런스별 핵심 행동 단계 수와 적용 교훈

[제안] 항구간 무역 시뮬레이션 장르 일반 구조를 참고할 때 핵심 행동은 대략 4단계(항로 선택→적재→항해→판매)로 압축 가능. 교훈: 초반 학습 부담을 줄이기 위해 항로·상품 선택지를 최소화하는 것이 유효하다는 설계 제안이며, 특정 레퍼런스 타이틀의 단계 수는 본 문서에서 확인된 근거가 없어 확정하지 않음.

12. 수치 KPI와 측정 방법

[제안] 검증 목표(예): 첫 세션 내 항해 완료율 60% 이상, 3세션 내 재방문율 30% 이상. 측정 방법은 세션 로그 기반 항해 시작/완료 이벤트 집계와 재방문 세션 수 트래킹을 제안. 현재 실측 KPI 데이터나 계측 코드 근거는 확인되지 않음(신뢰도 낮음).

13. UI, HUD, 컨트롤

[제안] 5개 핵심 UI 상태: ①항구/지도 메인 화면, ②항로 설정 화면, ③적재·시세 확인 화면, ④항해 진행(HUD) 화면, ⑤결과·정산 화면. cdp_06_move.png, cdp_07_trade.png 파일명이 이동·거래 화면 존재를 시사하나 상세 레이아웃은 미확인.

14. 로딩·빈 상태·에러·100개 이상 데이터·3배 긴 텍스트 대응

[제안] 항구/상품이 대량일 경우 목록 스크롤·검색 UI가 필요하며, 항로 데이터가 없는 초기 빈 상태에는 안내 문구 노출이 필요할 것으로 제안. 현재 이러한 처리 로직의 구현 여부를 확인할 근거는 없음.

15. 접근성

[제안] 색맹 대응을 위한 시세 등락 아이콘 병기, 텍스트 확대 옵션, 키보드/컨트롤러 대체 입력 지원을 제안. 접근성 구현 근거는 현재 파일 목록에서 확인되지 않음(신뢰도 낮음).

16. 시각·청각·햅틱 피드백

[사실] gen_bgm.cjs, gen_bgm.js가 배경음악 생성 스크립트로 존재. [제안] 항해 완료·거래 성사 시 사운드/시각 이펙트 피드백을 제공하는 것을 제안하나 구체 구현 확인은 되지 않음.

17. 구현 상태 매트릭스

[사실] 테스트 파일 존재 확인됨: fleetTradeFlow.test.js(무역-함대 흐름), mapHints.test.js(지도 힌트), mapView.test.js(지도 뷰), marketPrices.test.js(시장가격), navigation.test.js(항해/내비게이션), routeSummary.test.js(항로 요약), trade.test.js(거래). 각 파일의 실행 결과(통과/실패)는 본 문서에서 실행하지 않아 확인되지 않음.

18. 빌드·테스트 근거

[사실] package.json에 정의된 스크립트: dev(vite), test(node --test), build(vite build), preview(vite preview), serve(http-server dist). 이 스크립트들의 실제 실행 로그나 성공/실패 결과는 본 세션에서 관찰되지 않았으며, 존재하는 테스트 파일 목록만이 확인된 근거임.

19. 알려진 리스크와 실패 시나리오

[제안] 항로·시세 시스템의 학습 곡선이 가팔라 초반 이탈이 발생할 위험, 데이터 열람 권한 제약으로 인해 실제 플레이테스트 피드백(persona_playtest_feedback.md)이 설계에 반영되지 못했을 위험을 제안. 두 항목 모두 원문 확인 전까지 추정 단계임.
